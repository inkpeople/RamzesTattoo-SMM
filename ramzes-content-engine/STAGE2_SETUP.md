# RAMZES AI — подключение второго этапа

Этот этап добавляет код для аналитики, долгосрочной памяти, публичного мониторинга и ежедневных Telegram-сводок. Он не меняет работающий Render webhook и не разворачивает новые платные сервисы.

## Что появилось в коде

- Команды владельца `/lead`, `/leadstage`, `/booking`, `/publication`, `/metric`, `/memory`, `/analytics`.
- Связь метрики с конкретной публикацией через `publication=ID` в `/metric`.
- Расчёт вовлечённости только при наличии просмотров; конверсия заявка → запись — только при явной связи booking с `lead_id`.
- Таблицы для заявок, записей, публикаций, подтверждённых событий памяти, открытых источников и истории запусков агентов.
- Публичный мониторинг с Brave Search API (если есть ключ) и RSS fallback.
- GitHub Actions workflow для ежедневного запуска в 06:00 по Новосибирску.

## Данные из Tattoo Manager

В текущем репозитории нет подтверждённого API-коннектора к Tattoo Manager. Поэтому команды `/lead` и `/booking` пока являются безопасным ручным вводом владельца, а не автоматической синхронизацией с календарём/CRM. Не добавляй имена, телефоны, Telegram-ники, медицинские сведения и переписки клиентов. Чтобы обновить этап заявки: `/leadstage id=12; stage=qualified` (этапы: new, qualified, consultation, booked, completed, lost). В записи указывай `lead_id=12`, чтобы можно было посчитать конверсию. Для полной автоматизации нужен документированный API, webhook или согласованный экспорт из Tattoo Manager.

## Настройка отдельной базы RAMZES AI

Не создавай проект в чужой организации и не используй базу Tattoo Manager. Миграция находится в:

`ramzes-content-engine/supabase/migrations/202611170001_marketing_intelligence.sql`

Сначала должен существовать отдельный проект RAMZES AI и быть применена первоначальная миграция `202611160001_initial_ramzes_content_engine.sql`, затем — миграция второго этапа. В этой ветке миграции только добавлены в GitHub; в Supabase они не применялись.

После миграций:
1. Включи Data API для схемы/таблиц, используемых серверным адаптером. В новых проектах Supabase таблицы больше не открываются через Data API автоматически.
2. Проверь, что у таблиц включён RLS.
3. Не выдавай доступ `anon` и `authenticated`; доступ нужен только доверенному серверу через `service_role`.
4. Проверь healthcheck и чтение/запись тестовой записи после подключения.

## GitHub Actions Secrets

В репозитории открой Settings → Secrets and variables → Actions и добавь:

- `TELEGRAM_BOT_TOKEN` — токен только @RamzesContentEngineBot.
- `TELEGRAM_OWNER_ID` — личный Telegram ID владельца.
- `SUPABASE_URL` — URL отдельного проекта RAMZES AI.
- `SUPABASE_SERVICE_ROLE_KEY` — секретный ключ отдельного проекта RAMZES AI.

Не добавляй эти значения в код, коммиты или сообщения. `OPENROUTER_API_KEY` и `BRAVE_SEARCH_API_KEY` необязательны для запуска workflow: без OpenRouter мониторинг отправит список найденных ссылок без ИИ-анализа; без Brave Search будет использован RSS fallback.

Для Render-сервиса те же Supabase-переменные должны быть заданы только после создания и проверки отдельного проекта RAMZES AI. Не меняй webhook URL и токен.

## Важные ограничения

- GitHub Actions cron запускается не непрерывно, а один раз в сутки. Расписание активируется только после попадания workflow в default branch.
- Ежедневная бизнес-сводка требует настроенную базу RAMZES AI и четыре обязательных секрета выше.
- Закрытые охваты, рекламные бюджеты и статистика чужих аккаунтов недоступны без официального доступа.
- Публичная поисковая выдача не является полным мониторингом рынка.
- Публикации, ответы клиентам, массовые сообщения и рекламные действия не выполняются автоматически.
- PR остаётся Draft; ничего не объединять в production без отдельного согласования владельца.
