# RAMZES AI — план внедрения

## Цель

Развить текущий Content Engine в управляемую команду из 37 специализаций, сохранив существующий Telegram webhook, текущие команды и совместимость с Render. Сначала — безопасная архитектура и тесты; затем — подключение ролей по этапам.

## Текущее состояние (проверено по ветке ramzes-ai-agent-architecture)

- В `agents.py` есть 16 специализированных функций и `run_content_team` как оркестратор контентной цепочки.
- В `app.py` подключены `run_content_team` и `research_agent`.
- В `storage.py` уже есть необязательная интеграция с Supabase для истории чата, профиля бренда, публикаций и метрик. Она включается только при наличии URL, флага и service-role key.
- Текущий набор зависимостей небольшой: Flask, requests, gunicorn.
- Текущая ветка не должна автоматически попадать в production. Все изменения проходят PR и CI.

## Этап 0 — защита и инвентаризация

1. Сохранить действующие webhook URL, секреты, Render-команду запуска и переменные окружения.
2. Не менять webhook, токен Telegram, production service или настройки Render.
3. Зафиксировать текущие команды бота и контракт `model_call`.
4. Добавить smoke-тесты существующих сценариев до изменения маршрутизации.
5. Проверить текущие PR и базовые ветки перед объединением.

**Готово, когда:** существующие команды и webhook не изменены; baseline-тесты проходят.

## Этап 1 — управляющий агент и реестр специалистов

1. Создать единый реестр агентов с полями: id, роль, описание, триггеры, входы, выходы, инструменты, лимит токенов, необходимость веб-поиска, уровень риска.
2. Добавить классификатор задачи: контент, исследование, аудит, лиды, переписка, аналитика, кампания, отчёт.
3. Выбирать минимальную команду под задачу, а не запускать все 37 ролей.
4. Передавать агентам только нужный контекст и результаты предыдущих шагов.
5. Ввести общий бюджет вызовов и таймаутов на задачу.
6. Ограничить повторную редактуру одним циклом; при неуспехе возвращать черновик с объяснением.
7. Оставить fallback на существующую цепочку, если новый роутер недоступен.

**Готово, когда:** тестами подтверждено, что разные запросы выбирают разные наборы агентов, а простые задачи не запускают дорогую полную цепочку.

## Этап 2 — довести 17 существующих ролей до маршрутизации

- Подключить платформенную адаптацию отдельно для Threads, VK, Instagram и Telegram.
- Подключить аналитику только при наличии реальных метрик.
- Подключить планировщик кампаний к запросам о воронках и промо.
- Подключить менеджера сообщества к ответам на комментарии и сообщениям.
- Сохранить существующие этапы редактора и QA, не дублировать проверки.

**Готово, когда:** каждая роль имеет триггер, вход, формат результата и хотя бы один unit-тест.

## Этап 4 — память

1. Использовать существующий `storage.py` как базовый адаптер, не создавать второй независимый слой памяти.
2. Разделить память на: подтверждённые факты бренда, предпочтения, контент, метрики, кампании, гипотезы и журнал решений.
3. Хранить у каждой записи источник, дату, тип достоверности и срок актуальности.
4. Не превращать гипотезы агентов в подтверждённые факты автоматически.
5. Добавить экспорт/резервную копию и тесты отключённой БД.
6. Supabase использовать только если пользователь сам выделит доступный проект/лимит. Не создавать и не удалять проекты автоматически.

**Готово, когда:** бот продолжает безопасно работать без Supabase, а при включённой БД данные разделены по пользователю и типу.

## Этап 5 — бесплатные источники и мониторинг

1. Начать с RSS, публичных страниц, открытых поисковых результатов и официальных API с бесплатной квотой.
2. Добавить единый интерфейс источников: fetch → normalize → deduplicate → timestamp → cite.
3. Хранить URL, дату получения, дату публикации и фрагмент доказательства.
4. Вводить лимиты запросов и кэширование.
5. Для платформ с закрытой статистикой использовать только официально переданные пользователем метрики или разрешённые API.
6. При ошибке источника сообщать о пробеле, не заменять его выдуманными цифрами.

**Готово, когда:** исследовательские отчёты содержат проверяемые ссылки, дату и пометки «факт / гипотеза / неизвестно».

## Этап 6 — Telegram-отчёты и расписание

1. Для расписания использовать отдельный GitHub Actions workflow, не заменяющий webhook.
2. Отправлять отчёт через Telegram Bot API только в заранее настроенный owner chat.
3. Добавить ручной запуск workflow и dry-run.
4. Не запускать автоматическую публикацию, рекламу, массовую рассылку или личные сообщения.
5. Дедуплицировать отчёты и ограничить число уведомлений.

**Готово, когда:** workflow проверен вручную, секреты заданы в GitHub Actions Secrets, тестовое сообщение доставлено владельцу.

## Этап 7 — проверка и выпуск

- Unit-тесты реестра, маршрутизатора, памяти и каждого нового инструмента.
- Интеграционные тесты на mock model_call и mock источниках.
- Проверки prompt injection из внешних материалов.
- Проверки отсутствия секретов в логах и репозитории.
- Проверки лимитов вызовов и таймаутов.
- PR остаётся draft до прохождения CI и ручной проверки.
- Production обновляется только после отдельного согласования.

## Критерии успеха

- Простая задача: 1–2 вызова модели, без запуска всей команды.
- Сложная задача: только необходимые роли, ограниченный бюджет.
- Любое число/метрика имеет источник либо помечено как неизвестное.
- Никакая публикация или отправка клиенту не выполняется без разрешения.
- При отключении внешнего API бот сообщает о недоступности и сохраняет базовые функции.
- Никаких новых платных сервисов и изменений production без отдельного согласования.
