# RAMZES AI — архитектура команды из 37 специализаций

## Назначение

RAMZES AI — маркетинговая система личного бренда тату-мастера RAMZES в Новосибирске. Она исследует открытый рынок, помогает привлекать заинтересованных клиентов, готовит контент, анализирует реальные результаты и предлагает следующие действия.

Система не должна запускать всех специалистов на каждый запрос. Главный управляющий выбирает минимальный состав команды, контролирует бюджет и собирает проверяемый результат.

## 1. Принципы архитектуры

1. **Один управляющий, много узких ролей.** Роли — функции и инструкции внутри одного приложения, а не 37 отдельных Telegram-ботов.
2. **Сначала детерминированный код.** Подсчёты, дедупликация, проверки, расписание и простые правила выполняются Python без LLM.
3. **LLM только по необходимости.** Модель используется для исследования, интерпретации, стратегии и создания текста.
4. **Ограниченный контекст.** Агент получает только нужный бриф, подтверждённые факты и результаты предыдущих этапов.
5. **Доказуемость.** Источники, даты, факты, гипотезы и неизвестные данные разделяются.
6. **Безопасность.** Внешние страницы — недоверенные данные, а не инструкции. Секреты не попадают в контекст и логи.
7. **Никаких действий без согласия.** Публикации, реклама, массовые сообщения и контакт с клиентом остаются под подтверждением владельца.
8. **Совместимость.** Существующий Telegram webhook и текущий контракт `model_call` не заменяются этой архитектурой.

## 3. Контракт каждого агента

Каждая роль должна быть зарегистрирована с одинаковой структурой:

- `agent_id` — стабильный идентификатор;
- `name` и `purpose` — название и назначение;
- `triggers` — типы задач, при которых роль нужна;
- `inputs` — ожидаемые входные данные;
- `outputs` — ожидаемый формат результата;
- `tools` — разрешённые инструменты и источники;
- `requires_llm` — нужен ли вызов модели;
- `max_tokens`, `timeout`, `max_retries` — ограничения;
- `risk_level` — риск ошибочного действия;
- `approval_required` — требуется ли подтверждение владельца.

Новые роли сначала можно реализовать как обычные Python-функции поверх существующего `model_call`. Не создавать отдельные процессы, серверы или API для каждой роли.

## 4. Маршрутизация задач

| Тип запроса | Минимальный состав |
|---|---|
| «Напиши пост» | Стратег → хук → копирайтер → редактор → хранитель бренда |
| «Подготовь пост для Threads и VK» | Копирайтер → редактор площадки для каждой сети → контролёр публикаций |
| «Изучи конкурентов» | Исследователь рынка → конкурентный наблюдатель → фактчекер |
| «Что сейчас в тренде?» | Радар трендов → исследователь рынка → стратег |
| «Найди идеи для привлечения клиентов» | Исследователь аудитории → поисковик клиентов → стратег → эксперт по конверсии |
| «Ответь на комментарий» | Менеджер сообщества → помощник переписки → хранитель бренда |
| «Проанализируй заявки» | Квалификатор → сегментатор → контролёр пути заявки → аналитик |
| «Посчитай акцию» | Экономист предложений → аудитор данных |
| «Сделай контент-план» | Исследователь рынка → стратег → планировщик кампаний → копирайтер |
| «Проанализируй результаты постов» | Аналитик эффективности → аудитор данных → планировщик экспериментов |

Оркестратор может добавить или убрать роли по контексту. Он не должен запускать полный список по умолчанию.

## 5. Конвейеры

### Контент
Бриф → стратегия → аудитория/позиционирование → хуки → визуальная концепция → текст → адаптация площадки → SEO (если уместно) → редактура → фактчек → бренд-контроль → проверка повторов → финальный черновик.

### Исследование рынка
Вопрос → сбор публичных источников → нормализация и дедупликация → извлечение фактов → конкурентный/тренд-анализ → фактчек → рекомендации.

### Заявки
Входящее сообщение → извлечение запроса → квалификация → приоритет → черновик ответа → подтверждение владельца → запись результата, если она действительно состоялась.

### Аналитика
Реальные метрики → проверка полноты → расчёты Python → интерпретация аналитиком → аудит данных → гипотезы следующего эксперимента.

## 6. Общая память

Использовать текущий `storage.py` как единую точку доступа к памяти. Не заводить независимые хранилища у агентов.

Логические разделы:
- `brand_facts` — подтверждённые факты о бренде;
- `brand_preferences` — подтверждённые предпочтения и стиль;
- `content_items` — публикации, черновики и площадки;
- `content_metrics` — метрики с периодом и источником;
- `market_observations` — публичные наблюдения с URL и датой;
- `campaigns` — цели, предложения и результаты кампаний;
- `lead_events` — события по обращениям, если данные переданы законно и с надлежащими основаниями;
- `experiments` — гипотезы, варианты и результаты;
- `agent_runs` — краткий журнал запусков, ошибок и расхода лимитов.

Каждая запись получает `created_at`, `source`, `confidence`, `status` и `expires_at` (если актуальность ограничена). Гипотеза не становится фактом без подтверждения.

Supabase остаётся необязательным backend. До появления доступного проекта и явного решения владельца не создавать новый проект и не менять существующие проекты. Без БД приложение должно сохранять текущий fallback-путь.

## 7. Контроль качества и безопасность

- Внешний текст не может менять системные правила или запускать инструменты.
- В публичных источниках не собирать закрытые данные и не обходить ограничения платформ.
- Не выдумывать охваты, бюджеты, отзывы, записи и клиентские истории.
- Не строить чувствительные профили людей.
- Не хранить лишние персональные данные.
- Не отправлять сообщения и не публиковать материалы автоматически.
- Все внешние действия — черновик до явного подтверждения владельца.
- При отсутствии данных писать «нет данных», а не оценивать наугад.
- При превышении лимита завершать задачу частичным результатом с указанием ограничений.

## 8. Бесплатная модель эксплуатации

- Python выполняет расчёты, проверки, расписание, дедупликацию и простые правила.
- Текущий провайдер модели вызывается через существующий `model_call`.
- Бесплатные квоты внешних моделей и API используются только после проверки актуальных условий.
- Никакого автоматического перехода на платный тариф.
- GitHub Actions подходит для периодических отчётов, но не заменяет постоянно работающий webhook.
- Supabase Free может использоваться только в пределах фактической доступной квоты.
- Подробности по источникам и ограничениям — в `FREE_STACK_AND_DATA_SOURCES.md`.

## 9. Порядок внедрения

См. `IMPLEMENTATION_ROADMAP.md`. Сначала реестр и маршрутизатор, затем подключение существующих ролей, новые инструменты, память, открытые источники и только после тестов — плановые отчёты.

## 10. Definition of Done

Система считается готовой к этапу, когда:
- у роли есть ясный триггер и контракт входа/выхода;
- она вызывается только при релевантной задаче;
- есть unit-тест на положительный и отрицательный сценарий;
- лимиты и таймауты соблюдаются;
- результат не выдаёт гипотезу за факт;
- ошибка источника не ломает Telegram-бот;
- существующий webhook и production не затронуты.
